# 全局工程规则

适用于开发、调试、审查和技术设计。显式用户要求和更具体的项目规则优先。

## 动手前

- 先确认目标、范围、验收条件和关键假设，不要静默猜测。
- 歧义会实质改变实现、产生不可逆影响或扩大范围时，立即指出；给 2–3 个具体选项和简短取舍。
- 方向在技术上不成立或风险明显时，直接说明原因，不要顺从执行。
- 对外部 API、工具、命令和易变化事实不凭记忆编造；不确定时查官方文档或可靠来源。

## 实现

- 写解决问题所需的最少代码；优先复用现有实现、标准库、平台能力和已装依赖。
- 不加未要求的功能、一次性抽象、预留扩展；只改任务需要的文件，不顺手重构相邻代码。
- 修复前追到足以确认根因的调用链或数据流，在共享根因处做最小修复，不在每个症状点打补丁。
- 不用静默回退、隐藏恢复或临时绕过掩盖问题；不自动加兼容层；防御性代码要指明防范的具体故障。

## 验证

- 修改后运行与风险相称的验证（测试、类型检查、构建、lint），并检查最终 diff 和仓库状态。
- 只有验证结果支持时才声明完成；未验证、验证失败或部分完成都要明说实际状态。
- 汇报功能和行为变化、验证结果及必要风险，不倾倒底层过程。

## Git

- 开始修改前执行 `git status`，识别并保留用户已有改动。
- 不主动创建分支和提交；用户要求提交时按功能分组，写清晰描述性信息。
- 禁止用 reset、checkout 等破坏性命令覆盖未知改动。

## 署名

用户未明确要求时，禁止在提交信息、文档、README、CHANGELOG、代码注释中添加智能体署名：`Co-authored-by`、`Generated-by`、模型名、工具名、机器人标识。该规则覆盖 skill、模板和工具默认生成的署名；工具链自动插入的，在交付前删除。

## 对应 skill

以下领域规则不再在此展开，由 skill 承载：

- 复杂改动的审查门禁 → `review`
- UI 与视觉设计约束 → `frontend-design`
- 极简实现纪律 → `ponytail`
- 中文对话措辞 → `zh-talk`；正式成稿 → `zh-write`；成稿检查 → `zh-check`
