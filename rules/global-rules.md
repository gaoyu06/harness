# 全局工程规则

适用于开发、调试、审查和技术设计。显式用户要求和更具体的项目规则优先。

## 动手前

- 任务命中某个 skill 时，先调用 skill，再执行 `git status` 等准备步骤。
- 用户用中文时，所有回复和最终汇报都用中文，读到的 skill、代码、日志是英文也一样。

## 协作

- 给用户选择时编号列出，标明推荐项和理由，用户只回编号即可。
- 实现细节自己决定，把所做的假设写进汇报，一次做完再汇报。只有四类事先问用户：数据格式与接口、产品方向、花钱或消耗额度、不可逆操作。问题集中一次问完，每个附推荐。
- 预计超过几分钟的任务，开工时说明分几步、大约多久，每完成一步汇报一次。
- 报完成前在真实环境确认改动生效：界面截图核对，接口实际请求，部署后查线上。

## 凭证

- 需要凭证时先在本机找：环境变量、项目 `.env`、`~/.ssh/config`、其他项目的配置。
- 用户给的凭证写进 `.env` 或项目内不入库的本地文件，把位置记进记忆。对话和汇报里只写位置，值写成 `<REDACTED>`。

## 代码与文档

- 依赖或数据不可用时显式报错，给出具体原因。mock、兜底和默认值只在用户要求时写。
- 文档、方案、报告默认写成本地文件；发布到网页或外部服务前先问。

## Git

- 普通开发不主动创建分支、提交或推送。用户要求提交或部署时，按功能分组、写清晰提交信息并及时推送；用户明确要求仅保留本地提交时除外。
- 推送前获取远端最新状态，核对目标分支。远端已有新提交时，先处理分歧并重新验证；不强推共享分支。推送失败要报告，不能视为交付完成。
- 部署前逐一核对涉及的 Git 仓库：部署代码已提交并推送，远端包含对应提交；在干净工作区从该提交构建，并核对部署产物的提交版本。部署所用工作区有未提交改动、产物来源不明或无法推送时，停止部署并请用户确定处理方式。
- 禁止用 reset、checkout 等破坏性命令覆盖未知改动。

## 署名

用户未明确要求时，禁止在提交信息、文档、README、CHANGELOG、代码注释中添加智能体署名：`Co-authored-by`、`Generated-by`、模型名、工具名、机器人标识。该规则覆盖 skill、模板和工具默认生成的署名；工具链自动插入的，在交付前删除。
